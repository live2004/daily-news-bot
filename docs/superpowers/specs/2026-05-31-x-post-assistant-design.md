# X投稿 半自動アシスタント（x-post-assistant）設計書

- 作成日: 2026-05-31
- ステータス: 承認済み（実装計画フェーズへ）
- 関連資産: `daily-news-bot`（Telegram Bot・GitHubリポジトリを流用）

## 1. 目的と背景

働き盛りのビジネスパーソン（20〜50代、キャリアアップ・業務効率化・ビジネスマインドに関心が高い層）を
ターゲットに、X（旧Twitter）でのエンゲージメント向上と note へのトラフィック流入を最大化する。
手動でのトレンド調査・投稿作成コストを削減するため、Claude にトレンドを自律収集させ、
1日3回（朝・昼・夜）の投稿スケジュールに沿った**下書きを半自動で生成**し、人が承認して投稿する。

注力カテゴリ: 「AI・DX」「副業・ライフハック（情報リテラシー・キャリア防衛を含む）」「政治」「健康問題」。

## 2. 確定した方針（キーストーン決定）

| 論点 | 決定 | 理由 |
|---|---|---|
| 自動化の境界 | **下書き生成→人が承認→手動投稿**（半自動） | X API（有料）不要・無料。センシティブ題材の炎上/誤情報事故を人の承認で防ぐ。 |
| ランタイム | **`schedule` スキルのリモート定期実行（routine）** | Web検索が標準装備。Claudeサブスクを流用、追加課金・コード最小。PCの起動に依存しない。 |
| 生成サイクル | **ハイブリッド（cron 2本）**: 朝に朝・昼分を一括、夕方に夜の考察を再生成 | 鮮度（特に夜の暗号資産動向）と確認手間のバランス。 |
| 配信先 | **Telegram（既存 `daily-news-bot` のBot流用）** | スマホで受け取り→コピペ/予約投稿。新規構築不要。 |
| note記事カタログ | **`daily-news-bot` リポジトリに同梱** | 既存リポジトリで一元管理。記事の増減はJSON編集のみ。 |

## 3. 全体アーキテクチャ

人が最終承認して投稿する前提の「下書き生成パイプライン」。投稿基盤（X API）は持たない。

```
[schedule routine (cron)]
   → Claude が WebSearch でトレンド収集
   → note-articles.json を WebFetch で取得（最新の記事カタログ）
   → ペルソナ/制約に沿って下書き生成
   → 文字数バリデータで140字チェック & 自己リライト
   → Telegram Bot API へ送信（既存Bot流用）
   → 人がスマホで確認・微修正 → X に手動投稿 / 標準予約投稿
```

## 4. コンポーネント

### 4.1 ペルソナ／プロンプト資産（安定・低頻度更新）
元プロンプト（Role / Background / Constraints / Output）をテンプレ化し、routine の実行プロンプトに組み込む。
チェイン・オブ・ソート（Step1 トレンド収集 → Step2 ターゲット分析 → Step3 執筆 → Step4 品質監査）を維持する。
保存場所: `daily-news-bot` リポジトリ内（例: `x-post/persona.md`）。

### 4.2 note記事カタログ `x-post/note-articles.json`（随時更新）
各記事の「タイトル・実URL・テーマタグ」を保持。routine は実行時に raw.githubusercontent.com の
URL を WebFetch して最新を取得する（記事を増減しても routine 本体を触らない）。

スキーマ:
```json
{
  "articles": [
    {
      "id": "tachibana-200days",
      "title": "これが法治国家か──\"名誉毀損\"で200日。立花孝志氏が拘置所から出られない本当の理由",
      "url": "https://note.com/.../n/xxxxxxxx",
      "tags": ["リテラシー", "法的トピック", "社会"],
      "sensitive": true
    }
  ]
}
```
- `tags`: 朝/昼/夜のトレンド合致判定に使用。
- `sensitive`: true の記事は断定を避け、リテラシー/リスクヘッジの切り口に寄せる。

### 4.3 朝 routine（JST 07:00 頃起動）
1. WebSearch: 当日の国内ビジネス/経済/テック/働き方 ＋ ビットコイン等暗号資産 ＋ 情報リテラシー関連 ＋ 兵庫県政　＋　健康問題（統合失調症、糖尿病等）　の最新ニュース。
2. note-articles.json を取得。
3. 生成: **朝便（X完結型・ライフハックTips）** ＋ **昼便（note誘導型）** の2案。
   - 昼便は当日のトレンドに最も合致する記事を1つ選定し、解決する課題とベネフィットを明示。
   - 昼便は**スレッド形式**: 親ポスト（誘導文・URLなし・140字以内）＋ 子ポスト（リプライにURLのみ）。
4. 文字数バリデータで検証 → 140字超なら自己リライト。
5. Telegram へ送信（朝便・昼便を整形）。送信下書きは Telegram 履歴に残る（=ログ）。

### 4.4 夕方 routine（JST 18:00 頃起動）
1. WebSearch: 最新トレンド・速報を取り直す（鮮度重視）。
2. 生成: **夜便（トレンド考察型・共感/議論）** の1案。ビジネスパーソン視点の独自の切り口・考察。
3. 文字数バリデータで検証 → 自己リライト。
4. Telegram へ送信。送信下書きは Telegram 履歴に残る（=ログ）。

### 4.5 文字数バリデータ（決定的チェック）
LLM は日本語の文字数を誤カウントしがちなため、routine 内で**実カウントするスクリプト**を走らせる。
- ルール（ユーザーの編集方針に準拠）: **合計140字以内、URLはスレッド形式にするため、別投稿**。
- 計算: 各ポストの本文を Unicode コードポイント数（`[...str].length`）でカウント。URLは親本文に含めず子ポストへ分離するため、親ポストはURLを含まない前提で140字以内を判定。URLのみの子ポストは常に上限内。
- 絵文字は表示上1字として扱う（ZWJ連結絵文字は要注意エッジケース。多用しない方針なので実害小）。
- 140字超の場合は自己リライトを最大3回試行。収まらなければ「⚠️要短縮」ラベル付きで送信し、人が手当て。
- 補足: X 実機の重み付き文字数（twitter-text: CJK=2, 上限280, URL=23）に切り替える選択肢も将来的に可能。

## 5. データフロー / 出力フォーマット

Telegram には元プロンプトの出力形式そのまま＋メタ情報を付けて届ける。

朝 routine からのメッセージ例:
```
🗓 2026-05-31 朝便（X完結型・ライフハックTips）
[本文]
— 文字数: 112字 ✅

🗓 2026-05-31 昼便（note誘導型・スレッド）
[親ポスト本文（URLなし）]
— 文字数: 132字 ✅
↳ 子ポスト（リプライ）: https://note.com/.../n/xxxxxxxx
／誘導記事: tachibana-200days
```
夜便は夕方 routine から別メッセージで届く。

## 6. エラー処理・リスク対応

- **トレンド枯渇/低品質時**: 捏造で便乗せず、Focused_Categories のエバーグリーンTipsへフォールバック
  （禁止事項「事実確認の取れない便乗」を回避）。
- **Telegram 送信失敗**: 1回リトライ＋ログ。
- **センシティブ題材**（立花氏／情報操作系記事）: 人の承認が安全弁。ペルソナ側で「断定を避け、
  リテラシー/リスクヘッジの切り口に寄せる」を明示。`sensitive: true` で個別制御。
- **文字数オーバー**: 自己リライト失敗時は「⚠️要短縮」付きで送り、ブロックしない。
- **下書きログ**: Telegram のチャット履歴を下書きログとして用いる（全下書きがメッセージとして残る）。
  routine は remote 実行で永続FSを持たないため、リポジトリへの別途ログ追記は行わない（YAGNI）。

## 7. トーン＆マナー / 制約（出力品質ゲート）

- 各ポスト 140字以内（URL含めない）。
- 知的・論理的・実用重視のプロフェッショナルな「です・ます」調。煽り抑制、絵文字1〜2個まで。
- 禁止: 機械的な「note更新しました」告知 / ハッシュタグ3個以上（基本0〜1個）/ 未確認情報への便乗。

## 8. 人の運用フロー

1日2回 Telegram 通知 → 確認・微修正 → X に手動投稿（または8:00/12:00/20:00で X 標準予約投稿）。
記事を入れ替えたら `note-articles.json` を編集するだけ。

## 9. スコープ外（YAGNI）

- X API による自動投稿・完全自動運用。
- エンゲージメント分析ダッシュボード、A/Bテスト基盤。
- 画像/サムネ自動生成。
- 複数アカウント運用。

## 10. 実装計画で詰める統合詳細

- **(a) Telegram botトークンの routine への受け渡し方法**: `schedule` スキルのsecret/環境変数機構を使うか、
  routine プロンプト内で安全に参照するか（既存Botトークンを流用）。スキルの実行モデルに合わせて確定。
- **(b) note-articles.json の参照方式**: raw GitHub URL の WebFetch を基本とする。
  リポジトリが private の場合のアクセス方法（公開rawが使えない場合はプロンプト埋め込みにフォールバック）。
- **(c) cron 時刻のタイムゾーン換算**（JST→スキルが要求する形式）。
- **(d) 文字数バリデータの実行手段**（routine 内 Bash でのワンライナー or 小スクリプト）。
